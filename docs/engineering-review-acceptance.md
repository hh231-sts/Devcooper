## 实际运行与证据

所有运行记录均保存在本地 PostgreSQL，可用 `GET /api/chat/workflow-runs/{id}` 查看事件、证据和历史结论。

### 三方查证和重启恢复

运行 `e1704ae3-e495-4219-a9e6-4a888e71686a` 使用单独创建的 `manual/feedback-loop-acceptance` 仓库。其 JSON、文档及日志均明确标为模拟材料；日志是预置示例，未执行任何 CI 或测试，也没有创建可执行测试文件。

实际模型动作包括 Issue 向 PR 核查 `user_id` 要求、PR 向 CI 询问日志错误、CI 答复、PR 读取调用方并更新兼容性结论、PR 将答复交回 Issue。PR 结论保留三个版本，Issue 需求覆盖结论保留两个版本。

协作等待且没有未保存外部调用时，停止并重新启动专用验收服务：

| 角色 | 重启前模型/工具次数 | 恢复后的结果 |
|---|---|---|
| PR | 5 / 9，待处理工具 1 个 | 继续原任务，最终 7 / 13 |
| CI | 7 / 10，待处理工具 2 个 | 直接复用已保存决策，最终 7 / 12 |
| Issue | 6 / 6，等待答复 | 原收件箱和原预算继续，最终 7 / 8 |

重启前已有三个协作消息，恢复后仍保留。该运行最终为 `partial`：PR、CI 完成，Issue 在最终输出引用未保存证据编号时失败；已有结论、真实读取和答复未丢失，没有修补证据编号或自动重试。

另一次运行 `7a6c1493-839b-4166-a692-fdc8afc562a8` 专门验证未保存响应的中断：Issue 全文已经实际读取并保存，第二次模型调用保存意图后、响应落库前停止专用服务。重启后等待原租约自然到期，角色明确结束为“调用中断，未保存响应，不自动重试：model”；模型次数仍为 2、工具次数仍为 1，原证据 `d1cbf0ea-13f1-4eb6-8065-62ffbb17185e` 保持不变。Observer 生成了非法新增目标，综合阶段也未返回唯一结构化决策，均按实际失败记录，没有重试或补造模型响应；运行保存事实性部分报告。

### 固定版本与缺失 CI

运行 `f1cdda75-b106-4938-96f2-39292828d597` 在执行中将模拟 PR head 从 `08fa01ff449f5d7ef10775d0d8e37e26d3a21322` 更新到 `c2ed659093c8270483a48cbef60bac08eb0088bf`，同时编辑模拟 Issue。

运行快照仍保留原 Issue 正文、原 head、原 diff 和原代码证据。PR 经 Planner 请求追加 CI，两个角色均完成，运行状态为 `completed`，报告继续保留 CI 失败和 PR 阻塞门禁。新版本再次进行目标选择时，旧 CI 不再被选中，返回没有匹配失败运行。

独立门禁补充验收使用该固定失败 CI 的快照，在回滚事务中移除 CI 角色结果并提供“建议合入”的 PR 输入：综合阶段仍生成 `ci_merge_gate` blocker，服务端权威决策为 `hold`；PR 完成工具也将该输入改为“暂缓”并附加固定 CI 失败阻塞项。历史业务结果版本在回滚后不变。此项验证门禁取自固定事实，不依赖 CI 模型是否产出结果。

### 断线、同一目标与消息回写

运行 `ada23796-cb63-4fc2-92fd-8726911dd2f8` 从 Issue 流式接口提交，收到 `submitted` 后立即关闭客户端连接。后台仍继续读取九份材料，并完成 Issue 业务结果，最终保存了 13 次工具调用。后续新增角色目标不属于该独立 Issue 快照，运行保留部分报告与具体原因。

页面流式入口、聊天 `issue_agent.analyze_issue`、工程工作流三处人工提交核对，均绑定模拟 Issue `c873c39c-ea13-470a-9474-032fac42a85e`，角色均为 `issue_analyst_agent`，工具集合相同。聊天和工作流用于核对目标的新提交已取消，并核对终态为 `cancelled`。

补充审计发现 PR/CI 类本身仍残留一次性 `run()`，现已删除相应模型单次分析和规则回退。三个角色的 `run()` 统一提交持久化调查，`decide()` 统一推进原生工具决策；页面和聊天均通过角色入口进入共享模块。人工逐一调用三个角色，均返回 `queued`、明确目标和零调用初始预算，且工具集合不含自身分析入口；模拟验证运行随后取消。三种跨仓库 UUID 和确认计划中的外仓库 claim 均在创建运行前被拒绝。

对于旧 CI 运行的新失败 attempt 与另一个较新运行同时匹配 PR 的情况，在外层事务可回滚的环境中调用真实角色提交入口，核对目标解析与快照最终选择同一个最新执行记录（attempt 2）。临时记录和运行均回滚，没有发布调查或调用模型。

对已结束运行同时提供 `after` 和更大的 `Last-Event-ID`：服务按较大编号继续，收到的全部事件编号与数据库完全相同，末尾有 `settled`。原任务卡消息内容与 `final_answer` 相同。

补充修复并人工核对了聊天保存与报告回写的竞争：两个 PostgreSQL 会话分别持有运行行锁和保存迟到的聊天响应。数据库实际观察到 `wait_event_type=Lock`；释放锁后，过期 ORM 缓存被刷新，原卡、HTTP/SSE 返回内容及随后创建的 `AgentRun` 均沿用已完成报告及状态。临时写入全部回滚，原报告未改变。前端同时保留任务卡已经收到的最终报告，迟到的排队文本和聊天流末尾事件不会覆盖它；该前端分支已通过构建，页面行为见下述用户人工确认。

浏览器工具未能接入后，用户按明确步骤进行了实际页面验收并确认“已按步骤验证，均正常”：分析 Issue #101 后立即显示任务卡、可继续聊天、刷新后编号不变、原卡最终显示报告或具体失败，以及运行记录中的问答、证据和结论版本可展开。对应后台新运行是 `279ee53b-e88f-4eda-9637-384098b000f9`：Issue 成功完成，累计 7 次模型、13 次工具、结果 v1；整个运行为 `partial`，原卡内容与最终报告完全一致，持久化任务卡只有一条。页面结论来自用户实际操作，不宣称自动浏览器验收成功。

无快照的旧完成记录还通过可回滚的历史形状材料核对：列表和详情中的原报告、任务摘要均可读取，新预算字段为空对象、阶段为空，没有要求重跑旧任务；临时记录已回滚。现有重复启动迁移检查同时通过。
